PHASE 5 — Core Voting Engine and Privacy
Estimated duration: 7–8 active days

This is arguably the most technically important phase of Votexa.

We need to be particularly careful here.
Objective
Implement a functional voting system with duplicate-vote prevention and separation of voter identity from ballot choices.
A. Voting Interface
When voting opens, an approved voter sees their ballot.

For example:

President
- Candidate A
- Candidate B
- Candidate C
Vice President
- Candidate D
- Candidate E
Secretary
- Candidate F
- Candidate G
The voter selects one candidate per position.

Before submission, display a confirmation screen.

After confirmation, the ballot is submitted.
B. Voting Rules
The backend must enforce:
1. Only approved voters can vote.
2. Voting is permitted only during the configured voting period.
3. Each voter can submit only one ballot per election.
4. Every approved voter can vote for every position.
5. A candidate can vote if they are also an approved voter.
6. Votes cannot be modified after submission in the initial version.
7. The creator cannot view individual voting choices.
8. The platform admin cannot view individual voting choices.
C. Voting Privacy Architecture
We will not directly store:

user_id → candidate_id

Instead, we will design a privacy-preserving voting flow.

Conceptually:
Voter Identity
      |
      v
Eligibility Verification
      |
      v
One-time Voting Authorization
      |
      v
Anonymous Ballot Submission
      |
      v
Ballot Storage
      |
      v
Aggregate Results

We need to carefully implement:
- One-time voting authorization.
- Separation of voter participation records and ballots.
- Database constraints.
- Atomic transactions.
- Duplicate submission prevention.
- Protection against accidental identity leakage through logs and timestamps.
Important: Separating tables alone does not guarantee anonymity. We must design the token and ballot flow carefully. We should describe the finished project as privacy-conscious, not cryptographically anonymous or suitable for certified public elections without further security work.
Database tables
- ballots
- ballot_selections
We will also finalize the voter authorization mechanism.
Completion criteria
A registered and approved voter can successfully cast a ballot.

Duplicate votes are rejected by the backend.

Individual voting choices cannot be retrieved through normal admin or coordinator interfaces.

How we will work through each phase
I want to establish a development rule because you have repeatedly mentioned that you want to understand the project rather than simply copy code.

For every feature, we'll follow this sequence:

1. Understand

I'll explain what we're building, why it's needed, and how it works.

2. Architecture

We'll decide the frontend flow, backend API, database changes, and permissions.

3. Implementation

We'll write the code in manageable pieces.

4. Testing

You'll run it locally, test normal cases and failure cases, and understand the results.

5. Git checkpoint

Once the feature works, we'll commit and push it to GitHub.

6. Documentation

We'll update the Master Project Document so that our architecture and actual implementation remain synchronized.

We will not jump into the next feature until the current one is working.
My recommendations: What we should prioritize
There are three parts of Votexa that will matter most technically and during a resume discussion:
Priority	Component	Why it matters
1	Voting engine and privacy	Demonstrates backend design, transactions and security thinking
2	Election lifecycle and authorization	Demonstrates database relationships, RBAC and business logic
3	AI integration	Differentiates the project and demonstrates practical AI integration


The dashboard design is important, but it is not what will make Votexa technically impressive.

Also, we should not claim that Votexa is suitable for official government elections. It is an organization-focused election management prototype, and its privacy and security claims should accurately reflect what we implement and test.
